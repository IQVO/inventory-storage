# How to add a frontend remote

Use when adding a new screen/feature to this repo's `web/` Module
Federation remote, or when standing up a NEW remote for a bounded context
that doesn't have one yet. This is the Vite/React micro-frontend layer
that `warehouse-console` (the shell) lazy-loads — see that repo's
`.claude/rules/frontend-mfe.md` for the shell-side half of this contract.

## `vite.config.ts` must stay in OBJECT form, always

```ts
const IS_BUILD = process.argv.includes("build");
const PUBLIC_BASE = IS_BUILD ? "/mfes/<context>/" : "/";

export default defineConfig({
  base: PUBLIC_BASE,
  // ... Module Federation plugin config, etc.
});
```

Never convert this to the callback form
(`defineConfig(({ command }) => ({...}))`) to compute `base` dynamically.
Every remote's `vitest.config.ts` does `mergeConfig(viteConfig,
defineConfig({...}))`, and Vite throws `Error: Cannot merge config in
form of callback` on a function export — killing the ENTIRE test suite
for a one-line config change, not just the new test.

## A tiny, relative `dist/remoteEntry.js` after build is CORRECT

After a build with the `/mfes/<context>/` base, `dist/remoteEntry.js` is
~144 bytes and imports a RELATIVE path
(`./assets/virtual_mf-REMOTE_ENTRY_ID...js`) — grepping it for
`/mfes/<context>/` returns zero matches. That is expected, not a bug:
`dist/index.html` carries the absolute prefixed URLs, every JS chunk uses
relative ESM imports, and the module-preload helper resolves via `new
URL("../" + e, import.meta.url)`, which is origin-relative to wherever
`remoteEntry.js` was actually fetched from — exactly what a path-mounted
remote needs. Verify correctness by serving the built image and fetching
through the real gateway path, never by grepping the built file for the
expected prefix.

## `@warehouse/ui-kit` is a sibling checkout, not a registry package

`package.json` depends on it via `file:../../warehouse-ui-kit`. Any
domain-status color, chart, or shared layout primitive belongs in that
repo, not hand-rolled here — a remote reinventing its own palette instead
of consuming `StatusPill`/`tokens.css` is a bug, not a style choice
(visual consistency across the MFE boundary is the #1 place MFE UX
fails).

## Give the remote a `test` script, or added tests silently never run

`npm test` must map to `vitest run` in `package.json`. Several remotes in
this fleet historically shipped `package.json` with only
build/dev/lint/preview — `npm test` failed with `Missing script: "test"`,
and any `.test.ts` file added there silently never executed, invisible
unless someone ran `npm run` and actually read the script list. Confirm
this repo's `web/` CI job (`web:` in `.github/workflows/ci.yml`) actually
invokes `npm test`, not just `npm run build`.

## The Docker build recipe (packaging as a deployable nginx workload)

Three traps, in order of how much time they cost when hit blind:

1. **Base image must be `node:22-bookworm-slim`, not an alpine or newer
   node image.** This repo's `package-lock.json` was generated by npm 10
   and carries no Linux entries for Vite's platform-specific optional
   dependencies (`@rolldown/binding-linux-*`, `lightningcss-linux-*`).
   npm 11 rejects that lockfile outright with `EUSAGE "lock file out of
   sync"`; glibc (not musl) is what matches the published `*-gnu`
   bindings.
2. **Do NOT install from the committed lockfile, and do NOT reuse a host
   `node_modules`.** Both leave the native binding missing
   (`Cannot find native binding ... @rolldown/binding-linux-*`, a known
   npm/cli optional-dependency bug). The working recipe: `rm -rf
   node_modules package-lock.json` in the ui-kit build stage (it arrives
   as a named BuildKit context from a developer checkout), `COPY
   package.json ./` only, then `npm install --no-save`.
3. **`@warehouse/ui-kit` must be supplied as a named BuildKit context**,
   since it's a sibling checkout, not a registry dependency:
   ```bash
   docker build --build-context uikit=../../warehouse-ui-kit \
     -t warehouse/<context>-frontend:local .
   ```

See this repo's own `web/Dockerfile` for the complete, working, heavily
commented recipe — copy it rather than re-deriving these three traps from
scratch for a new remote.

## Wiring into `warehouse-infra`'s deploy

A new remote isn't deployed automatically — `warehouse-infra`'s
`local.services` map and this repo's own Helm chart (`frontend.enabled`
value, default `false`) both need updating. See `warehouse-infra`'s
AGENTS.md for the Terraform side of this; this repo only needs to ship a
working chart with `frontend.enabled` wired to a toggle.

## Key commands

```bash
cd web
npm ci
npm run lint        # oxlint
npx tsc -b           # typecheck
npm test             # vitest run — confirm this actually runs your new test
npm run build         # tsc -b && vite build -> dist/
```

CI's `web:` job runs this exact sequence against a dual checkout (this
repo + `IQVO/warehouse-ui-kit@develop`) — reproduce that locally by
symlinking or checking out `warehouse-ui-kit` as a real sibling if `npm
ci` behaves differently than CI.
